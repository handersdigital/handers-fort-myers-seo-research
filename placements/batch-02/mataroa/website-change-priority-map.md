A request to “fix the website” often combines several different jobs: correct a broken action, clarify a service, improve discovery, connect a campaign, and make follow-up easier. Treating all of them as one redesign makes the first useful decision harder to see.

## Name the broken decision

I would begin with one customer path and describe the point where it fails. Can the visitor understand the service? Confirm the service area? See enough evidence? Complete the action? Receive a useful confirmation? Reach the right person?

The answer turns a vague website request into an observable problem. It also shows which systems and people are involved. A form failure and a search-visibility gap may appear on the same page, but they do not share the same repair.

## Rank changes by consequence and evidence

The first queue should favor changes that block a high-intent visitor, publish an incorrect fact, break measurement, or leave an inquiry without an owner. Each proposed change needs a source, an accountable person, a verification method, and a rollback note when the risk is meaningful.

Visual preferences still matter, but they should not displace a broken call link or an inaccurate service claim. A priority map makes that tradeoff explicit.

## Connect the website and the operating path

Search, advertising, pages, forms, scheduling, and follow-up are separate tools only in the account list. To the customer, they are one experience. A useful plan checks the handoffs between them and records what remains unknown.
